# ドメインモデリング

**ドメインの設計は開発者本人が行う。** AI はここにあるモデルを提案・生成しない（質問への回答とレビューのみ）。

進め方は教材「ドメイン駆動設計 モデリング/実装ガイド」と「ドメイン駆動設計 サンプルコード&FAQ」に従う。
教材は有償の資料のため、**本文・図・コードをこのリポジトリに転記しない**。参照するときは章番号とタイトルだけを書く（例:「モデリング/実装ガイド 第3章 3.1 集約」）。PDF もコミットしない。

## 作成する図と順番

| 順番 | 成果物 | ファイル | 目的 |
|---|---|---|---|
| 1 | システム関連図 | `system-context.md` | システムと外部（利用者・Google・Stripe など）の関係を把握する |
| 2 | ユースケース図 | `usecases/<context>.md` | 誰が何をするかを洗い出す。ユースケース層のクラスと対応する |
| 3 | ドメインモデル図 | `domain-model/<context>.md` | ルール・制約と集約の境界を表す。**ユビキタス言語の正本** |
| 4 | オブジェクト図 | 必要なときだけ | 具体例でルールを確認する（複雑な集約のみ） |

- 図は **Mermaid** で書く（GitHub の PR 上でそのまま表示され、レビューしやすいため）。
- 図はコードと同じ PR で更新する。モデルを変えたのに図が古い状態にしない。
- 集約の境界・コンテキストの分け方を決めたら、理由を ADR に残す。

## ユビキタス言語

- ドメインモデル図に書いた言葉を正本とする。
- コードは英語で書くため、日本語と英語の対応だけを [glossary.md](./glossary.md) で管理する。図と食い違ったら図を正とし、用語集を直す。

## モデリングで決めること（技術側から見た論点）

アーキテクチャ（[consistency.md](../architecture/consistency.md)）を決めるには、以下の答えが必要になる。答えはモデル図と ADR に書く。

- 在庫は「いつ」減らすか（カート投入時 / 注文時 / 決済完了時）。引き当てた在庫を、決済されないまま何分保持するか
- 注文の状態と、状態が移る条件（どの状態からキャンセルできるか）
- 注文時点の価格・商品名を注文側に写して持つか（後から商品が変わっても注文は変わらない、など）
- どこまでを1つの集約にするか（強い整合性が必要な範囲はどこか）
- イベントソーシングを適用する集約はどれか（[ADR-0004](../adr/0004-event-sourcing-scope.md)）
