# ADR-0004: イベントソーシングの適用範囲と自作のイベントストア

- 状態: 採用（適用する集約は、モデリング後に追記する）
- 日付: 2026-11-07

## 背景

イベントソーシングを学びたい。ただし、全ての集約に適用すると複雑さが増え、CRUD で済む部分まで手間が増える。
教材ではイベントソーシングを CQRS と別のものとして説明しており、実装方法は扱っていない。そのため、このプロジェクトで独自にルールを決める。

## 検討した選択肢

### 適用範囲
- **A. 状態の移り変わりと経緯に意味がある集約だけに適用する**
  - 良い点: 効果がある箇所に集中できる。状態を保存する方式と比べて学べる。
  - 悪い点: 2種類の永続化の方式が混ざる。
- B. 全ての集約に適用する
  - 悪い点: 商品マスタやカートなどは経緯に意味がなく、読み取りモデルの手間だけが増える。

### 実装
- **A. 自作する**
  - 良い点: 追記・バージョンの確認・状態の復元・プロジェクションの仕組みを自分で理解できる。
  - 悪い点: 実装とテストの量が増える。
- B. EventSauce を使う
  - 良い点: 設計が整っていて、フレームワークに依存しない。
  - 悪い点: 仕組みを書かずに済んでしまい、学習の目的に合わない。
- C. spatie/laravel-event-sourcing を使う
  - 悪い点: Laravel に強く依存し、ドメイン層を独立させる方針と合わない。

## 決定

- 適用範囲は A。**最初の対象の候補は Ordering の注文**。どの集約に適用するかは、モデリングで決めてからこの ADR に追記する。
- 実装は A（自作）。イベントストアは `modules/Shared/Infra` に置き、ドメイン層には「集約のイベントを読み込む・追記する」interface だけを置く。
- 設計のルールは [consistency.md の 4章](../architecture/consistency.md#4-イベントソーシング) に従う。

## 影響

- 注文の一覧などの参照系は、読み取りモデル（プロジェクション）から取得する。読み取りモデルは遅れて更新されることを、画面の設計で考慮する。
- イベントの形式を変えるときの手順（`event_version` と変換）を、最初の変更時に Task として作る。
