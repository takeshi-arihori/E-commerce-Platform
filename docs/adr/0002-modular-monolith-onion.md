# ADR-0002: モジュラーモノリスとオニオンアーキテクチャ

- 状態: 採用
- 日付: 2026-11-07

## 背景

DDD で設計し、境界づけられたコンテキストを分けたい。一方で、開発者は1人で、マイクロサービスにすると運用の負担が学習の妨げになる。
DDD の進め方は教材（モデリング/実装ガイド、サンプルコード&FAQ）に従う。

## 検討した選択肢

### A. モジュラーモノリス（1アプリケーション、コンテキストはディレクトリで分ける）
- 良い点: デプロイ・運用が1つで済む。コンテキストの境界を、ネットワークの問題なしに学べる。後から分割できる。
- 悪い点: 境界を守る仕組みがないと、すぐに依存が混ざる。

### B. マイクロサービス
- 良い点: 境界が物理的に強制される。
- 悪い点: 分散トランザクション・サービス間通信・運用の負担が大きい。MVP の規模に見合わない。

### C. 通常の Laravel 構成（`app/Models`・`app/Http` など）
- 良い点: Laravel の情報が多く、速く作れる。
- 悪い点: ドメイン層を独立させられず、DDD を学ぶ目的に合わない。

### アーキテクチャ: オニオン / クリーン / ヘキサゴナル
教材がオニオンアーキテクチャを採用しているため、それに合わせる。層の名前も教材に合わせる（domain / usecase / presentation / infra）。

## 決定

- A のモジュラーモノリスを採用する。
- 各コンテキストの中は**オニオンアーキテクチャ**にする。
- ディレクトリは**コンテキスト → 層 → 集約**の順に分ける（[modules.md](../architecture/modules.md)）。
- 依存のルールは Deptrac か Pest の arch テストで CI が検査する。

## 理由

教材は「層を最上位のパッケージにする」ことを勧めている。複数コンテキストを1つのアプリケーションで扱う場合は、コンテキストをパッケージで分けることも示されている。両方を満たすため、最上位をコンテキストにし、その中で層を最上位にする。コンテキストが最上位にあると、後からアプリケーションを分割しやすい。

## 影響

- Laravel の規約（`app/` 配下の構成、Eloquent をどこでも使う書き方）から外れるため、ServiceProvider でのバインドなど、つなぎの記述が増える。
- ドメイン層で Laravel の便利な機能（Collection など）が使えない。
- コンテキストの分け方はモデリングで決まり次第、[modules.md](../architecture/modules.md) を更新する。
