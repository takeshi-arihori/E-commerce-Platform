# ADR-0006: 非同期処理（キュー・Outbox・冪等性）

- 状態: 採用
- 日付: 2026-11-07

## 背景

- 注文の受付はアクセスが集中しやすい。
- Stripe Webhook はすぐに応答しないと再送される。
- コンテキストをまたぐ更新は、1トランザクションにしない方針（[ADR-0002](./0002-modular-monolith-onion.md)）。

## 検討した選択肢

### キューの基盤（ローカル）
- **A. Redis + Laravel Queue（Horizon）**: Laravel の標準で情報が多い。Horizon でジョブの状態を見られる。
- B. DB を使うキュー: 追加のミドルウェアが不要だが、負荷が集中する箇所を DB に寄せることになる。
- C. 最初から SQS（LocalStack）: 本番に近いが、ローカル環境が重くなる。

### DB 更新とイベント発行の整合性
- **A. Outbox パターン**: DB への保存と発行するメッセージを同じトランザクションで書く。
- B. コミット後にキューへ直接投入する: 投入に失敗するとメッセージが消える。

## 決定

- キューは A（Redis + Laravel Queue + Horizon）。ジョブはユースケースを呼ぶだけにし、将来 SQS に差し替えられるようにする。
- イベント発行は A（Outbox）。受け側は Inbox で重複を捨てる。
- 注文の受付は `202 Accepted` で受け付け、ワーカーで処理する。
- 二重実行を防ぐため、注文 API は `Idempotency-Key` を必須にする。
- 詳細は [consistency.md の 6〜8章](../architecture/consistency.md#6-outbox--inbox)。

## 影響

- 注文の結果がすぐには分からないため、画面で状態を確認する仕組み（ポーリングなど）が必要になる。
- メッセージは「少なくとも1回」届くので、全ての受け側を冪等にする必要がある。
- ワーカー・リレー・スケジューラーを別プロセスとして起動する必要がある。
