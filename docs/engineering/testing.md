# テスト方針

## TDD

- **Red → Green → Refactor** で進める。変更前に、意図した理由でテストが失敗することを確認する。
- コミットも `test:` → `feat:` → `refactor:` の順にする（[delivery-workflow.md](./delivery-workflow.md#コミット)）。

## 層ごとのテスト

| 対象 | 種類 | DB | 確認すること |
|---|---|---|---|
| 値オブジェクト・エンティティ | 単体 | 使わない | 生成時の不変条件、状態を変えるメソッド、再構成（教材: サンプルコード&FAQ 第7章） |
| イベントソーシングの集約 | 単体 | 使わない | **Given**（過去のイベント）→ **When**（コマンド）→ **Then**（新しいイベント、または例外） |
| ユースケース | 単体 | 使わない（Fake のリポジトリ） | 集約の組み合わせ方、権限、戻り値 |
| リポジトリ・クエリサービス | 統合 | **実 DB** | 保存と取得で値が一致する、検索条件、ロック |
| プロジェクション | 統合 | 実 DB | イベントから読み取りモデルが正しく作られる、2回処理しても変わらない |
| API | Feature | 実 DB | ステータスコード、レスポンスの形、認証・認可 |
| フロントエンド | コンポーネント（Vitest + Testing Library） | - | 表示と操作 |
| 主要な流れ | E2E（Playwright） | 実環境 | ログイン → カート → 注文。MVP の後半で追加する |

- テストの名前は日本語で、条件と結果が分かるように書く（例: `在庫が足りない場合、引き当てると例外になる`）。
- Fake は本番の実装と同じ interface・同じ契約を守る。
- モックは外部サービス（Stripe・Google）との境界でだけ使う。
- テスト用の DB は開発用と分ける。テストごとにデータを片付ける。

## 並行実行テスト

ロック・冪等性・イベントストアの競合検出は、**実際に同時に実行して**確認する。

- 例: 在庫10個の商品に、20件の引き当てを同時に実行し、成功が10件・失敗が10件・在庫が0になることを確認する。
- 例: 同じ `Idempotency-Key` の注文を同時に5回送り、注文が1件だけできることを確認する。
- 例: 同じ集約に、同じバージョンから2つのイベントを同時に保存し、片方だけ成功することを確認する。
- 実行方法（複数プロセス / 複数の DB 接続）は環境構築後の Task で決める。

## CI で実行するもの

- Backend: Pint（チェックのみ）、Larastan、依存方向の検査、Pest（単体・統合・Feature）
- Frontend: lint、型検査、Vitest、build
- 並行実行テストも CI で実行する（時間がかかりすぎる場合は別ジョブにする）
